# zsh-docker-compose-exec-mode 憲法

## 中核原則

### CLIファーストとシンプルさ
`dce` は単一のCLIエントリーポイントで、サブコマンド（`start`、`end` など）を一貫した動作で提供しなければならない。利用中のサービス名はユーザーが明示選択し、プラグインが推測してはならない。ヘルプとエラーメッセージは簡潔かつ行動可能であること。

### 安全なコンテナ実行
execモード開始前に `docker compose` の存在と対象サービスの起動を検証し、満たさない場合はガイダンス付きで中止すること。デフォルトは非rootで実行し、rootでの実行はユーザーの明示的同意を必要とする。コンテナ内実行中であることを明示し、ホストの状態を不要に変更してはならない。

### セッションの明確化と隔離
execモード開始時にプロンプトやコンテキストを設定し、対象サービス名をセッションに保持すること。終了時には元のプロンプト・シェル設定・trapを確実に復元する。ネストしたセッションやゾンビ状態を検出し、回復手順を示して拒否すること。

### 最小依存と性能
依存は zsh 組み込みと `docker compose` のみに限定し、追加ツールは正当化が必要。起動および各コマンドのオーバーヘッドは開発用ノートPCで100ms未満を目標とする。可能な限りPOSIX互換を維持する。

### テスト可能性とドキュメント整合
各リリースは `dce start` → コマンド実行 → `dce end` までのスモークテスト（欠落サービス時のエラー経路を含む）を再現可能な形で提供する。READMEの使用例は実装と常に同期し、破壊的変更には移行手順を明記する。

### 日本語優先コミュニケーション
このリポジトリのドキュメント、仕様、レビュー、エラーメッセージ、テンプレートは原則として日本語で記述すること。外部依存で英語表記が必要な場合のみ例外を認め、理由を記録する。

## 追加の制約
- 互換性: zsh 5.8+ を前提とし、特定バージョン依存の機能を使う場合は理由を明記する。
- 安全性: コンテナやホストのファイルを意図なく変更しない。破壊的操作をデフォルトにしない。
- UX: プロンプトのマーカーは視認性が高く曖昧さがないこと。エラーには失敗コマンドと次の手順を含める。
- 可観測性: 主要操作（start/end、サービス検出失敗）は `DCE_DEBUG=1` 時にstderrへタイムスタンプ付きで出力することが望ましい。

## 開発ワークフロー
- 挙動が変わる設計変更は実装前に issue/spec で合意する。
- セッション処理やプロンプト変更を行う場合はスモークテストを先に追加・更新する。
- README と `--help` 出力をリリース前に同期する。
- セッションライフサイクルや安全チェックに触れる変更は必ずレビューを受ける。
